# AIHR 项目复盘：从招聘看板到效果评估闭环

## 项目起点

AI 招聘推荐上线后，业务方常常只问一句：“AI 推荐的面试率是不是更高？”

这个问题看似简单，却不能只用两组转化率回答。AI 和人工推荐的人群可能本来就不同；招聘结果有明显滞后；转化下滑也可能来自顾问跟进或招聘流程，而不一定是模型退化。

因此，AIHR 的目标从一开始就不是做招聘管理系统，而是做一个能支持以下决策的分析 MVP：

1. AI 推荐与人工推荐的效果差异是否值得关注？
2. 这个差异在控制可观测结构差异后是否还存在？
3. 当前数据和样本成熟度是否足以支撑结论？
4. 效果变化应优先排查模型、数据、团队操作还是招聘流程？

## MVP 范围如何收敛

项目早期有很多可做的方向：职位市场数据、候选人匹配、复杂机器学习模型、LLM 报告、权限系统和告警通知。

MVP 最终只保留一条主线：

```text
招聘推荐事件
  -> 漏斗与成熟队列
  -> AI/人工效果比较
  -> 选择偏差调整
  -> 数据质量与漂移监控
  -> 可解释的业务结论
```

这样做的原因是，作品集项目需要先证明“能可靠地回答一个复杂业务问题”，而不是展示一组彼此松散的功能。

## 从 0 到现在的关键迭代

### 1. 先定义事件级数据，而不是先画图

第一版思路容易落到“按天汇总的看板指标”。但只保留日度聚合后，模型版本、顾问团队和推荐来源等筛选维度会变得不一致，也无法处理推荐后的结果滞后。

现在的核心粒度是一条 `recommendation_id`，并通过 `fact_funnel_event` 保存推荐、联系、回复、面试、Offer、入职事件。页面需要统一筛选时，直接从事件级推荐事实查询；`mart_*` 表保留给可复用的日度、队列、漂移和告警汇总。

这项取舍对应了 [ADR 0002](adr/0002-event-level-dashboard-filters-and-monitoring-rollups.md)。

### 2. 合成数据不再只是随机数据

公开招聘漏斗数据很难同时满足真实性、隐私和可复现性。项目没有把随机数直接做成图表，而是用固定种子生成可复现的推荐与事件数据，并刻意植入五种可检测场景：

- AI 推荐的候选人经验更高，形成选择偏差。
- 2026 年第二季度销售岗位的 AI 模型效果下降。
- 华东招聘团队在 2026 年 5 月出现联系延迟。
- AI 推荐分数在版本切换后发生漂移。
- 最近推荐未达到 30 天观察窗口，形成未成熟队列。

对应测试会验证这些场景是否真的能被数据生成器稳定复现和发现。这样合成数据的用途是验证分析链路，而不是模拟真实企业的绝对结果。

### 3. 从“谁的转化率高”升级为“是否可比较”

直接比较 AI 与人工面试率有选择偏差：两组候选人的经验、岗位类别、地区、资深度和顾问团队可能不同。

当前版本使用推荐发生前的可观测变量训练 Logistic Regression 倾向得分，保留共同支持区间，并使用 stabilized IPTW 估计调整后的两组面试率。页面还展示：

- 原始差异与 95% 置信区间。
- 共同支持范围和保留样本量。
- 截尾前后的最大权重。
- 调整前后的 SMD 协变量平衡诊断。

这不会把观察性数据包装成因果实验。页面和 API 会明确标记结果为“调整后的关联分析”。

### 4. 从“模型掉了”升级为结构化排查

转化率下降有多个可能原因：流量结构变化、输入特征漂移、模型版本问题、顾问联系延迟或招聘流程变化。

因此监控页同时检查：

- 基准期与当前期的来源级面试率变化。
- 按模型版本、岗位和地区的流量及效果趋势。
- 数值特征的 PSI、类别特征的 JSD、推荐分数均值变化。
- 基于分群变化、数据异常、招聘团队和模型信号生成的结构化诊断结论。

这让“发现异常”之后还有一条可执行的排查路径。

### 5. 让看板先给结论，再给证据

早期的分析页面更接近“图表集合”。当前页面统一使用：

```text
共享筛选范围
  -> 核心指标
  -> 自动分析结论
  -> 图表和明细
  -> 页面内 AI 助手追问
```

首页聚合效果、质量、漂移和分群机会；各页面再解释漏斗瓶颈、趋势波动、效果调整和异常样本。这是从“展示数据”向“支持业务阅读”做的产品化改造。

## 当前 MVP 的能力边界

已完成：

- Streamlit 前端、FastAPI 分析 API、SQLAlchemy 数据访问、SQLite 本地运行、MySQL Docker 运行。
- 统一日期、来源、岗位、地区、模型版本、顾问团队筛选。
- 漏斗、趋势、效果评估、监控、数据质量、机器学习洞察和 AI 辅助解读。
- 合成数据、数据集市、SQL 质量检查、pytest 和 ruff。
- Kaggle LinkedIn 职位/技能数据导入到 raw 层的脚本和 SQL 分层设计。

未把它包装成“已解决”的内容：

- 当前招聘漏斗结果是合成数据，不代表真实企业或真实 AI 模型效果。
- 倾向得分只能调整已观测变量，不能排除未观测混杂；不能得出因果结论。
- 机器学习洞察使用最近 5,000 条记录在线训练，AUC、Accuracy 和特征贡献主要用于交互式探索，不是离线生产模型评估。
- 外部职位市场数据已具备导入和 SQL 分层，但尚未接入主 Dashboard 的用户流程。
- 当前 Docker Dashboard 通过 `app/Home.py` 兼容入口加载首页；本地开发推荐直接使用 `app/首页.py`。
- CI、截图/GIF、线上 Demo、权限和告警通知仍是作品集发布前可继续补强的部分。

## 面试时如何讲

### 30 秒版本

> 我做的是一个 AI 招聘推荐效果评估与监控系统。它不只展示漏斗，而是解决 AI 与人工推荐不可直接比较、招聘结果滞后、模型与流程问题难以区分这三个问题。我用事件级数据、成熟队列、倾向得分 IPTW、SMD、漂移监控和异常诊断，把效果评估和业务排查放进同一个 Dashboard。

### 3 分钟版本

1. 先说明业务问题：AI 推荐的总体转化率更高不等于 AI 本身更有效。
2. 说明数据设计：推荐事实与漏斗事件分离，使用固定种子合成数据植入可验证异常。
3. 说明严谨性：用成熟队列处理结果滞后，用 IPTW 和 SMD 降低可观测选择偏差。
4. 说明落地：FastAPI 提供统一筛选 API，Streamlit 将结论、证据和行动建议呈现出来。
5. 说明边界：这是观察性、合成数据上的分析框架，不宣称真实企业因果效果。
