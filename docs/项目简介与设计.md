# AI-Hiring-Monitor 项目简介与设计

## 1. 一句话简介

AI-Hiring-Monitor 是一套面向招聘业务的数据分析系统，用于评估 AI 推荐相对于人工推荐的招聘漏斗表现，识别模型和流程异常，并将分析结果转化为可执行的业务建议。

## 2. 项目简介

招聘团队上线 AI 推荐后，不能只看推荐数量或总体转化率。由于 AI 和人工推荐面对的岗位、候选人质量、地区和顾问团队可能不同，直接比较面试率容易产生误判；同时，面试、Offer 和入职存在明显时间滞后，最近月份的数据也可能尚未成熟。

本项目围绕这些问题构建一套端到端分析系统：

```text
招聘业务事件
  -> 数据清洗与质量检查
  -> 招聘漏斗和队列指标
  -> AI/人工效果比较
  -> 选择偏差调整
  -> 漂移与异常监控
  -> Dashboard 与业务结论
```

公开版本使用固定随机种子生成的合成数据，不包含真实候选人或前公司数据。合成数据不是简单随机数，而是模拟岗位难度、候选人质量、顾问联系速度、模型版本和招聘结果滞后等真实业务机制，以便验证分析方法是否能够发现预先植入的问题。

## 3. 项目要解决的业务问题

### 3.1 效果问题

- AI 推荐是否比人工推荐带来更高的有效面试率？
- 控制岗位、地区和候选人差异后，AI 与人工的差异是否仍然存在？
- AI 在哪些岗位和地区有效，在哪些场景下效果较差？

### 3.2 诊断问题

- 转化率下降来自模型、数据、顾问操作还是招聘流程？
- 新模型版本上线后，是否出现局部岗位效果退化？
- 候选人结构和推荐分数是否偏离历史基准？

### 3.3 数据可信度问题

- 当前月份的入职率是否因观察窗口不足而被低估？
- 漏斗事件是否存在重复、缺失、逆序和数据延迟？
- 指标是否能追溯到明确的分子、分母和时间口径？

## 4. 目标用户

| 用户 | 主要决策 |
|---|---|
| 招聘业务负责人 | 是否扩大 AI 推荐使用范围，哪个团队需要改进 |
| 招聘数据分析师 | 维护指标、分析分群、定位异常、输出结论 |
| 推荐模型负责人 | 判断版本效果、输入漂移和局部退化 |
| 招聘顾问负责人 | 识别联系延迟、团队执行差异和漏斗损失 |

## 5. 核心指标设计

主指标：

```text
推荐后30天合格面试率
= 推荐后30天内完成合格面试的推荐数 / 已达到30天观察窗口的推荐数
```

基础漏斗：

```text
推荐曝光
  -> 顾问联系
  -> 候选人回复
  -> 面试
  -> Offer
  -> 入职
```

系统同时展示阶段转化率和累计转化率：

- 阶段转化率：面试数 / 回复数。
- 累计面试率：面试数 / 推荐数。
- 累计入职率：入职数 / 推荐数。

所有比例指标必须同时展示分子、分母、样本量和置信区间；未成熟队列不能直接参与完整入职效果比较。

## 6. 数据设计

### 6.1 内部招聘事实

生产结构预留以下表：

```text
dim_candidate       候选人匿名属性、经验、学历、技能簇
dim_job             岗位类别、等级、地区、薪资和难度
dim_recruiter       顾问、团队和地区
dim_model_version   模型版本和上线时间
fact_recommendation 推荐来源、模型分数、排名和时间
fact_funnel_event   联系、回复、面试、Offer、入职事件
```

### 6.2 分析数据集市

```text
mart_daily_funnel       日度漏斗指标
mart_cohort_conversion  推荐月份队列指标
mart_ai_effectiveness   AI/人工效果和调整结果
mart_feature_drift      特征漂移指标
mart_monitoring_alert   告警、阈值和证据
```

### 6.3 数据来源边界

公开岗位或官方就业统计数据只用于丰富岗位市场画像；招聘推荐和后续转化事件使用合成数据，未来只能接入经过书面授权的脱敏 ATS 数据。

GitHub 公开仓库不包含真实候选人、前公司数据、完整抓取原文、数据库备份、Token 或密码。

## 7. 分析方法设计

### 7.1 原始效果比较

比较 AI 与人工推荐的推荐量、漏斗转化率、累计面试率和累计入职率，同时计算比例差及 95% 置信区间。

### 7.2 选择偏差调整

AI 和人工推荐不是随机分配，因此先使用推荐发生前的候选人和岗位特征估计倾向得分，再进行加权或匹配：

```text
原始样本
  -> 倾向得分模型
  -> 检查共同支持区域
  -> 加权/匹配
  -> SMD 平衡性检查
  -> 调整后效果估计
```

禁止把联系、回复、面试等处理后变量放入倾向模型。结果表述为调整后的关联或估计效果，不将观察性分析包装成严格因果结论。

### 7.3 SMD 平衡性

使用标准化均值差异比较 AI 与人工组在经验、学历、岗位类别和地区等特征上的平衡性，并展示调整前后变化。

### 7.4 漂移监控

- PSI：用于工作年限、模型分数等数值特征的分箱漂移。
- Jensen-Shannon divergence：用于岗位类别、地区等类别分布漂移。
- 业务指标监控：对累计面试率、联系率等指标建立滚动基准和告警阈值。

### 7.5 异常归因

将总体变化拆解成：

```text
总体指标变化
  = 分群占比变化
  + 分群内部转化变化
```

再将异常定位到岗位、地区、顾问团队、推荐来源或模型版本。

## 8. 系统架构

```text
Streamlit Dashboard
        |
        v
FastAPI Analytics API
        |
        v
Service Layer
指标计算、统计分析、监控任务
        |
        v
SQLAlchemy / MySQL
        |
        +-- raw/staging：原始与清洗数据
        +-- dim/fact：业务维度和事实
        +-- mart：Dashboard 查询结果
```

本地开发可以使用 SQLite，Docker Compose 使用 MySQL；两者通过同一套 SQLAlchemy 模型和服务接口访问。

## 9. Dashboard 设计

### 总览

展示推荐量、AI 占比、联系率、累计面试率、Offer 率、入职率、趋势和当前告警。

### 招聘漏斗

展示 AI 与人工在各环节的数量损失、阶段转化率和累计转化率，支持岗位类别和地区筛选。

### 趋势分析

按日期观察 AI 与人工累计面试率变化，定位模型版本或业务周期造成的变化。

### 效果评估

展示原始差异、置信区间、样本量，并明确标识当前结果尚未进行选择偏差调整。

### 效果监控

比较基准期和当前期的转化率，按严重程度展示异常状态；后续扩展 PSI、JSD 和输入特征分布。

## 11. 作品集表述

### 简历短版

> 设计并实现 AI 招聘推荐效果评估与监控系统，基于 Python、SQL、FastAPI 和 Streamlit 完成招聘漏斗、分群效果、趋势监控及异常诊断；使用固定种子合成数据复现选择偏差、招聘结果滞后和模型效果退化场景，并通过置信区间、倾向得分和 SMD 设计调整后评估方案。

### 面试讲解版

> 这个项目的重点不是做一个招聘管理系统，而是回答 AI 推荐是否真的有效，以及效果发生变化时如何定位原因。我先定义了从推荐到入职的指标树，再通过成熟队列处理招聘结果滞后；由于 AI 与人工推荐不是随机分配，又设计了倾向得分和 SMD 方案来降低选择偏差；最后把效果评估、漂移监控和异常证据放进同一个 Dashboard。

## 12. 当前限制

- 当前公开版本使用合成数据，不能代表真实企业招聘效果。
- 当前效果比较还是未调整差异，倾向得分和 SMD 尚未接入 Dashboard。
- 当前监控主要是基于转化率的窗口比较，PSI/JSD 尚未接入。
- 当前数据模型仍以日度聚合指标为主，尚未扩展为完整推荐和事件明细。
- LLM 解释功能尚未接入，未来只能处理已计算的结构化指标。
