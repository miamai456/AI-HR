## 一、SQL 高频题（先练这个，筛人第一关）

> 练习建议：在项目本地库里直接跑（PostgreSQL `aihr` 库），边写边验证。表：`fact_recommendation`(r)、`fact_funnel_event`(f)、`dim_job`(j)、`dim_candidate`(c)。

**⭐Q1 窗口函数：每个岗位类别里，按面试率排名的前 3 个地区**
```sql
SELECT job_category, region, interview_rate, rk
FROM (
  SELECT j.job_category, j.region,
         COUNT(DISTINCT CASE WHEN f.stage='interviewed' AND f.status='completed' THEN r.recommendation_id END)::float
           / NULLIF(COUNT(DISTINCT r.recommendation_id),0) AS interview_rate,
         ROW_NUMBER() OVER (PARTITION BY j.job_category ORDER BY ... DESC) AS rk
  FROM fact_recommendation r
  JOIN dim_job j ON r.job_id = j.job_id
  LEFT JOIN fact_funnel_event f ON f.recommendation_id = r.recommendation_id
  GROUP BY j.job_category, j.region
) t WHERE rk <= 3;
```
考点：`ROW_NUMBER()` / `RANK()` 区别（并列是否跳号）；窗口函数 vs GROUP BY。

**⭐Q2 去重：同一推荐在漏斗事件表只算一次（防止重复计数）**
```sql
SELECT recommendation_id, stage, COUNT(*) FROM fact_funnel_event
GROUP BY recommendation_id, stage HAVING COUNT(*) > 1;
```
考点：为什么唯一约束重要（AIHR 里 `recommendation_id + stage` 唯一）。

**⭐Q3 留存/队列：各月推荐队列的 30 天面试率**
```sql
SELECT DATE_TRUNC('month', r.recommended_at) AS cohort_month,
       COUNT(DISTINCT r.recommendation_id) AS recommended,
       COUNT(DISTINCT CASE WHEN f.stage='interviewed' AND f.status='completed'
                        AND f.event_at <= r.recommended_at + INTERVAL '30 days'
                      THEN r.recommendation_id END) AS interviewed_30d,
       ... / NULLIF(COUNT(DISTINCT r.recommendation_id),0) AS rate_30d
FROM fact_recommendation r
LEFT JOIN fact_funnel_event f ON f.recommendation_id = r.recommendation_id
WHERE r.recommended_at <= CURRENT_DATE - INTERVAL '30 days'  -- 成熟队列
GROUP BY cohort_month;
```
考点：成熟窗口概念（把 AIHR 知识直接搬进 SQL）。

**Q4 漏斗：AI vs 人工各阶段人数（一行一个来源）**
```sql
SELECT r.source,
  COUNT(DISTINCT r.recommendation_id) AS recommended,
  COUNT(DISTINCT CASE WHEN f.stage='contacted' THEN r.recommendation_id END) AS contacted,
  COUNT(DISTINCT CASE WHEN f.stage='interviewed' THEN r.recommendation_id END) AS interviewed
FROM fact_recommendation r LEFT JOIN fact_funnel_event f
  ON f.recommendation_id = r.recommendation_id AND f.status='completed'
GROUP BY r.source;
```
考点：`COUNT(DISTINCT CASE WHEN ...)` 经典写法；LEFT JOIN 防漏。

**Q5 环比/同比**
```sql
SELECT period, recommended,
  recommended - LAG(recommended) OVER (ORDER BY period) AS mom_diff,
  recommended * 1.0 / NULLIF(LAG(recommended) OVER (ORDER BY period),0) - 1 AS mom_rate
FROM (SELECT TO_CHAR(DATE_TRUNC('month', recommended_at),'YYYY-MM') AS period,
             COUNT(*) AS recommended FROM fact_recommendation GROUP BY 1) t;
```
考点：`LAG()`；除零保护 `NULLIF`。

**Q6 JOIN 陷阱**
- LEFT JOIN 后计数膨胀：一对多时 DISTINCT 主键；
- 面试常问："内连接和左连接区别"、"JOIN 后行数变多怎么排查"（答：看是否一对多、是否该用子查询去重）。

**Q7 慢查询怎么优化**（口答题）
答：先 EXPLAIN 看执行计划；缺索引补索引（AIHR：复合索引 `ix_recommendation_analysis_filters`）；避免 SELECT *；大表预聚合（AIHR 的 mart 集市思路）；分页用游标/键集分页。

**Q8 你项目里 SQL 用在哪？**
答：SQL 分层参考（`sql/ddl`、`sql/staging`、`sql/marts`、`sql/quality_checks`）+ SQLAlchemy ORM 日常查询；数据质量检查本身就是 SQL 思维的规则化。

## 二、业务分析题（"指标异动"是最高频）

**⭐Q9 面试率下降了 20%，怎么分析？（必考套路，背框架）**
答：四步。
1. **确认口径与真实性**：是不是计算口径变了？数据有没有延迟/缺失？（先查数据质量，AIHR 思路）
2. **拆时间**：哪一天开始降？是趋势性还是偶发？看同比/环比。
3. **拆维度**：按来源（AI/人工）、岗位、地区、团队、模型版本拆，找"谁在降"（AIHR 的五类诊断就是干这个）。
4. **找原因假设并验证**：流量结构变化？模型版本切换？运营动作？（联系延迟）流程变化？用数据验证每个假设，最后给结论+建议下一步。
> 加分：先说"先确认是不是真的降（置信区间/成熟度）"，再说拆解。

**Q10 让你给业务定一个核心指标，怎么选？**
答：① 和业务目标直接挂钩（北极星）；② 可衡量、数据可得；③ 能影响（可行动）；④ 防止"只看一个指标被刷"——配套护栏指标（AIHR：面试率是主指标，联系率是护栏）。

**Q11 留存率怎么定义？新老用户分开吗？**
答：留存 = 某期用户在后 N 期仍活跃的比例；必须按 cohort（首次活跃月）分组、新老用户分开，因为行为模式不同。

**Q12 一个指标涨了，你怎么判断是"好涨"？**
答：拆结构（量增还是率增）、看是否以牺牲其他指标为代价（护栏）、看是否可持续（趋势+周期）、看置信区间是否显著、排除口径/数据问题。

## 三、统计基础题

**Q13 假设检验步骤？**
答：设 H0/H1 → 选检验方法 → 定显著性 α → 计算统计量与 p 值 → 决策。要讲清第一类错误（α，假阳性）和第二类错误（β，假阴性，1-β=功效）。

**Q14 p 值怎么解释？（易错）**
答：假设 H0 为真，观察到当前或更极端结果的概率。**不是**"H0 为真的概率"，也不是"有效果的概率"。

**Q15 正态分布/中心极限定理？**
答：样本均值在样本量足够大时近似正态（CLT），这就是为什么能用 z/t 检验；注意小样本、偏态数据要用非参数或 bootstrap。

**Q16 相关 vs 因果？（AIHR 直接衔接）**
答：相关≠因果，可能有混杂/反向因果/巧合。AIHR 里 AI 面试率高可能是"经验高"混杂造成的，所以用倾向得分调整，且仍只能叫关联。

**Q17 相关性用什么衡量？**
答：连续-连续用 Pearson（线性）、Spearman（秩）；类别用卡方检验/φ 系数；注意非线性相关 Pearson 会低估。
