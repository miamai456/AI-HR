# 第 8 课：面试问答 50 题（先自己答，再看参考答案）

> 用法：每题先闭卷答 30 秒，再对照参考答案。红色标记的题**必考**，先背熟。

## A. 项目与业务（1-10）

**1. 介绍下你的项目（必考）**
答：用 3 分钟版（见 01 课）：业务问题 → 数据设计 → 方法严谨性 → 落地形态 → 边界。

**2. 这个项目解决什么业务问题？（必考）**
答：三个：AI/人工不可直接比较（选择偏差）；招聘结果滞后；效果下降原因不明（数据/流量/模型/团队/流程）。

**3. 为什么不能直接比 AI 和人工的面试率？（必考）**
答：两组候选人结构不同（AI 推荐的高经验多、岗位/地区分布不同）；结果有滞后；未成熟队列会系统性低估近期表现。

**4. 数据从哪来？是真的吗？（必考）**
答：公开招聘漏斗数据涉及隐私拿不到，用固定种子生成 10 万条合成推荐、约 60 万条事件，刻意植入 5 类可检测异常；外部还有 Kaggle LinkedIn 职位数据做市场分析。合成数据验证的是分析链路，不是真实业务数值。

**5. 这个项目是给谁用的？**
答：招聘业务负责人和运营团队——判断 AI 是否值得继续投、效果掉了查哪里。

**6. 为什么选"面试率"作为主效果指标？**
答：面试是漏斗中最早可反映"推荐质量"的业务结果，30 天窗口即可成熟；Offer/入职滞后更长（60/90 天）。

**7. 和普通 BI 看板（PowerBI/Tableau）比，你的项目有什么不同？**
答：① 口径统一（筛选一致、指标字典）；② 结论可解释（结论→证据→风险→建议）；③ 结论可验证（结构化 API + pytest）；④ 有统计严谨性（成熟队列、IPTW、SMD、漂移监控）而不只是画图。

**8. 你怎么定义"推荐效果"？**
答：推荐在面试/Offer/入职等业务结果上的转化表现，主指标 30 天成熟面试率，分子是 30 天内完成面试的成熟推荐数，分母是推荐满 30 天的推荐数，按推荐日期归因。

**9. 项目最大的挑战是什么？**
答：从"画看板"到"结论可信"的转变——最大的坑是早期只有日度汇总，无法按模型版本/团队下钻、无法算成熟队列，所以重构为事件级事实层 + 集市层。

**10. 如果业务方说"AI 面试率就是更高，不用那么复杂"你怎么回应？**
答：承认观察到的差异，但说明两组结构不同，直接结论可能误导资源决策；给出倾向得分调整后的差异作为更稳的估计，并说明观察性局限。

## B. 数据与统计（11-25）

**11. 什么是成熟队列？为什么需要？（必考）**
答：只有观察窗口结束的推荐才进入成熟率分母（面试 30 天、入职 90 天）。否则近期表现被系统性低估。

**12. 什么是倾向得分？（必考）**
答：用推荐前可观测变量估计"这条推荐来自 AI 的概率"，用于构造可比人群。

**13. IPTW 是什么？稳定化 IPTW 和普通 IPTW 区别？（必考）**
答：逆概率加权，给每条样本按"实际来源概率的倒数"加权，构造伪随机样本。稳定化版用处理组占比做分子，减少极端权重。

**14. 为什么权重要截尾到 0.1~10？**
答：极端倾向得分产生极大权重，少数样本主导结论；截尾降低方差，代价是估计的是更稳定可比较的人群。

**15. 什么是共同支持？没有会怎样？（必考）**
答：AI/人工倾向得分分布的重叠区间；没有重叠的样本无可比对照，模型外推不可信，应剔除。

**16. SMD 是什么？0.1 阈值怎么来的？（必考）**
答：标准化均值差，两组协变量均值差/合并标准差；|SMD|<0.1 是经验上"可接受平衡"的常见标准。它是诊断指标，不是严格证明。

**17. 加权后差异收窄说明了什么？**
答：说明一部分原始差异来自协变量结构差异（选择偏差），调整后更接近可比人群的关联差异。

**18. 你的结论是因果吗？为什么不是？**
答：不是。观察性数据 + 只能调整已观测变量，未观测混杂（候选人真实质量、职位紧急度、顾问主观判断）无法排除；需要随机实验或更强的识别策略才能谈因果。

**19. PSI 和 JSD 区别？（必考）**
答：PSI 用于数值特征分布漂移（分桶后占比差的对数加权）；JSD 用于类别分布差异（对中点分布的 KL 散度平均）。阈值：PSI <0.1/0.25，JSD <0.05/0.2。

**20. 漂移了怎么办？**
答：先结合样本量看是否稳定，再按模型版本/岗位/地区/团队拆解定位，输出结构化诊断（五类归因），触发数据质量复核。

**21. 逻辑回归预测的目标和特征是什么？（必考）**
答：目标"是否进入面试"；特征：来源、推荐分数、经验、学历、岗位、地区、资深度、模型版本、团队；最近 5000 条在线训练。

**22. 为什么选逻辑回归而不是 XGBoost？**
答：二分类适配、训练快（看板实时）、可解释、与倾向得分一致；MVP 稳和解释优先于最高分数；后续可升级 XGBoost/LightGBM + SHAP。

**23. 特征贡献怎么算的？是因果吗？**
答：特征值 × 系数，方向性信号，平均绝对贡献排序；是关联解释不是因果。

**24. 为什么用孤立森林做异常检测？**
答：无监督无需标注、适合表格数据、处理多维组合、速度快；结合预测残差找"特征罕见 + 预测/实际不一致"的样本。

**25. AUC 和 Accuracy 哪个更值得看？**
答：AUC 衡量排序/区分能力，对类别不平衡更稳健；Accuracy 依赖阈值和分布。本项目正负样本不平衡，AUC 更关键，Accuracy 辅助。

## C. 数据建模与架构（26-35）

**26. 什么是事实表、维度表、集市表？你的分层怎么设计？（必考）**
答：维度表描述主体（候选人/岗位/顾问/模型版本），事实表记录事件（推荐、漏斗事件），集市表预汇总（每日漏斗、成熟队列、效果、漂移、告警）。真相在事件级事实层，集市只是查询加速。

**27. 为什么事件级数据比日度汇总好？（必考）**
答：维度不丢失（可按下钻）、可处理滞后（成熟队列）、口径一致（统一筛选）。

**28. `recommendation_id + stage` 唯一约束的作用？**
答：防止同一阶段重复计数，保证漏斗统计正确。

**29. 指标的时间归因怎么做的？**
答：按推荐日期归因（recommended_at），1 月推荐 3 月面试仍算 1 月队列。

**30. 统一筛选怎么实现的？（必考）**
答：前端 ui.py 双状态筛选（草稿/应用）+ URL 参数 + 本地文件三通道保存；后端所有接口接收同 6 个参数，服务层 `_recommendation_query` 统一生成查询；计算都在后端，前端不二次计算。

**31. 为什么计算放后端而不是前端？**
答：口径一致（一处计算多处复用）、可测试（pytest 直接测服务层）、可缓存（Redis/进程缓存）、前端只负责呈现。

**32. 缓存怎么设计的？数据更新怎么失效？**
答：前端 `st.cache_data ttl=60`；API 侧上下文快照缓存 60 秒；`system_data_version` 作为缓存失效边界，数据版本变化时快照重建；ML 预测进程内 64 项 LRU 60 秒。

**33. 数据量大了怎么办？（必考）**
答：事件级加复合索引；mart 集市预聚合；ML 在线采样 5000 条；快照物化 + Redis 缓存 + RQ 预热；后续可离线调度全量训练入模型集市。

**34. 你怎么验证指标口径不变？**
答：指标字典文档 + pytest 把分子分母/成熟窗口写成断言（test_seed、test_analytics、test_marts）。

**35. 数据库从 SQLite 到 PostgreSQL 迁移你怎么做的？**
答：Alembic 版本迁移（migrations/versions/），迁移脚本处理 schema；配置分层切换，环境变量 `AIHR_CONFIG_FILE` 指向不同环境配置。

## D. 工程与代码（36-42）

**36. 项目怎么测试的？（必考）**
答：pytest 覆盖配置、种子可复现性、5 类异常检测、API 结构、统一筛选、效果/监控/质量/ML 输出、集市幂等刷新、助手服务；ruff 检查风格。

**37. 讲讲你代码的分层？**
答：API 层（参数/响应/缓存）→ 服务层（统计/ML 计算）→ 数据层（SQLAlchemy 查询）；边界模块转发保持整洁。

**38. 怎么保证响应结构稳定？**
答：Pydantic response_model，字段契约固定，前端依赖稳定字段。

**39. 部署方式？**
答：Docker Compose（PostgreSQL + API + Streamlit + health check）；运维组件 Redis/RQ/Prometheus/Grafana/OpenTelemetry；操作端点 Bearer Token。

**40. 安全上做了什么？**
答：敏感配置不提交（.gitignore、secrets.toml、config.local.ini）；操作端点鉴权；LLM Key 只在服务端，Streamlit 不接触 Key。

**41. 你遇到最难修的 bug？**
答：口径不一致问题（日度汇总缺维度）→ 重构为事件级；这是设计层面的修复，最有价值。（也可讲你实际遇到过的）

**42. 项目里你最喜欢/最自豪的代码？**
答：`_propensity_adjustment`——几十行把倾向得分、共同支持、稳定化 IPTW、截尾、SMD 串成一条可测的流水线；或者 `seed.py` 的 5 类可检测异常设计。

## E. 行为与开放题（43-50）
**43. 如果给你一个月继续做，你做什么？**
答：① 模型升级：XGBoost/LightGBM + SHAP，离线训练入模型集市；② 因果补强：双重稳健估计（DR）/工具变量或 A/B 设计建议；③ 时间序列预测推荐量与转化；④ 真实数据接入（ATS 授权）验证；⑤ CI + 截图/GIF + 线上 Demo。

**44. 你觉得自己这个项目哪里还不完善？**

**45. 用一句话总结项目？**
答："AIHR 不是只展示招聘图表，而是用数据分析、统计诊断和机器学习方法，系统性回答 AI 推荐是否有效、为什么变化、哪里异常、下一步该查什么。"

**46. 你作为数据分析师，这个项目锻炼了你什么？**

**47. 你平时怎么做数据分析？方法论？**

**48. 你熟悉 SQL 吗？这个项目里 SQL 用在哪？**
答：项目有 sql/ 目录（DDL、staging、mart、质量检查），SQLAlchemy ORM 日常查询，SQL 参考实现用于数据仓库风格部署；我写过 XX（如实说）。

**49. 你了解 A/B 测试吗？和本项目关系？**
答：A/B 是因果推断的金标准；本项目数据是观察性的，所以用倾向得分调整做关联分析，并明确不宣称因果；如果业务允许，建议对 AI/人工推荐做随机分流实验来验证。

## F. AI 分析助手专属问题（51-54）

**51. AI 助手和普通 ChatGPT 有什么区别？为什么不让它直接算？**
答：三个关键区别：① **只解释不算数**——它只能引用传入的结构化上下文（`assistant/context` 快照），提示词明确禁止编造指标、日期、团队；② **强制结构化**——非流式要求返回 JSON（conclusion/evidence/risks/recommendations），流式要求固定 Markdown 标题；③ **可信度信封**——服务端根据样本量和数据质量自动标注置信度，低置信度答案被强制降级为"探索性判断"。基础指标计算永远在服务层，LLM 不参与。

**52. 上下文怎么传给 LLM？token 成本怎么控制？（追问）**
答：`_compact_context_data` 做上下文压缩：列表按白名单截断（如 trend 只留 6 行、drift_metrics 只留 5 行、数据质量只保留未通过的检查）、字符串截到 1000 字符、去掉 cached/latency 等元信息；最后只带最近 8 条对话。实测一次分析约 444 tokens。

**53. 助手失败/没配置怎么办？**
答：三级降级：① 配置了 DeepSeek 但请求失败 → 客户端对 408/429/5xx 自动重试 3 次（指数退避）；② 前端 API 调用失败 → 自动降级为本地规则回答（`local_analysis`，基于结构化事实拼结论/事实/推断/建议）；③ 完全没配置 Key → 直接走本地规则。保证看板任何时候都能解释指标。

**54. 怎么防止 LLM 胡说八道？**
答：四道防线：① 提示词约束只能引用上下文、禁止因果声明；② 上下文本身是压缩后的真实指标快照；③ 服务端 `apply_trust_guard`——低置信度答案强制加"探索性判断"前缀和风险提示；④ 响应结构与 trust 信封一起返回，前端展示"分析依据"折叠区让用户看到样本量、时间范围、质量状态。

## 高分技巧

1. **先结论后细节**：任何问题先一句话给结论，再展开，不要从背景讲起。
2. **主动讲边界**：因果、合成数据、样本量的局限自己先交代。
3. **带数字**：10 万推荐、60 万事件、5000 条训练、0.1~10 截尾、±0.1 SMD、PSI 0.1/0.25、JSD 0.05/0.2。
4. **衔接演示**：讲到方法时说"这个我演示给你看"，把面试变成带路。
