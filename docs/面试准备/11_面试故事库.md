> 讲出来比背任何八股都加分——因为它证明了你有**数据质量意识**和**定位问题的能力**。

## 故事一：数据质量检查"误报"了 44.7 万行非法状态

### 现象（怎么发现的）

打开"数据质量"页面，发现两项 **fail/high**：
- `Invalid source, stage, or status enums`（非法枚举）：影响 447,782 行
- `Anomalous record ratio`（异常记录占比）：影响 448,103 行，占比 64%

直觉告诉我不对劲——64% 的记录都是异常，那"异常"的定义本身就值得怀疑。

### 排查过程

1. 先看质量检查的实现（`analytics_core.py` 的 `_invalid_enum_count`）：
   - 它检查三类非法值：来源（ai/human）、阶段、状态；
   - 合法的状态白名单是 `{completed, skipped}`；
   - 合法的阶段顺序表是 `{contacted → hired}`（5 个阶段）。
2. 再查种子数据生成器（`seed.py`）：
   - 每条推荐会生成一个 **`recommended`（推荐）阶段事件**，作为漏斗入口；
   - 未到达的阶段状态写的是 **`not_reached`**（语义：该阶段未发生）。
3. 对照后发现**口径不一致**：
   - 种子数据里合法的阶段是 6 个（含 `recommended`），合法状态是 2 个（completed / not_reached）；
   - 质量检查的合法集合只有 5 个阶段、2 个状态（skipped 而不是 not_reached）；
   - 于是 10 万条 `recommended` 阶段事件 + 约 34.8 万条 `not_reached` 状态事件全被误报为"非法"。

### 修复

两处统一口径（`src/aihr/services/analytics_core.py`）：

```python
# 1) 合法状态补上 not_reached（种子数据的真实语义）
VALID_EVENT_STATUSES = {"completed", "skipped", "not_reached"}

# 2) 合法阶段补上 recommended（业务漏斗：推荐→联系→回复→面试→Offer→入职）
EVENT_STAGE_ORDER = {
    "recommended": 0, "contacted": 1, "replied": 2,
    "interviewed": 3, "offered": 4, "hired": 5,
}
```

### 修复后

数据质量页变为 **12 项检查、0 失败、1 警告**（警告是"未来时间戳"321 条——对应刻意植入的"近期推荐事件尚未成熟"场景，属于合理的关注项）。

### 面试怎么讲（30 秒）

> "我在准备演示时发现数据质量页把 64% 的事件标记为非法枚举，排查后发现是**质量校验的合法值字典**和**种子数据生成器的口径**不一致：校验漏了 `recommended` 阶段和 `not_reached` 状态。我统一了这两处口径，修复后 12 项检查全部通过。这正好体现了数据质量检查的价值——**它真的能暴露口径问题**。"

### 这个故事证明了你什么

- 会**怀疑数据**而不是照单全收（64% 异常 → 先质疑异常的定义）；
- 会**读代码定位根因**（检查器 vs 生成器口径对比）；
- 有**统一口径意识**（这正是数据分析师的核心素养）；
- 修复后**用测试和接口验证**（pytest 全绿 + 接口复查）。

## 故事二（可选）：测试环境与运行环境的坑

### 现象

本地跑 `pytest` 时，一批用到临时目录（`tmp_path`）的测试报 `PermissionError`，而项目代码本身 62 项测试是过的。

### 排查与结论

- 报错都发生在 pytest 的**临时目录清理/创建**环节（`os.scandir` 被拒绝），不是业务断言失败；
- 指定 `--basetemp` 到工作目录后大部分恢复，确认是**执行环境的临时目录权限**问题；
- 在正常终端里运行 `pytest` 不受影响（76 项全部通过）。

### 面试怎么讲（如果被问到"你遇到过环境问题吗"）

> "遇到过 pytest 临时目录的权限报错，先确认是测试框架的临时目录问题而不是业务逻辑问题（把测试临时目录指到项目内验证），最终在正常环境下 76 项测试全绿。定位技巧是：**先区分'测试框架问题'和'代码问题'**，不要一上来怀疑业务代码。"
