# 第 3 课：数据模型详解（维度表 / 事实表 / 集市表）

## 一、先理解一个核心概念：事实表 vs 维度表

- **维度表（dim_）**：描述"谁/什么/在哪"。候选人、岗位、招聘顾问、模型版本——它们基本不变，是分析时用来**切片的**。
- **事实表（fact_）**：记录"发生了什么"。"谁在什么时候推荐了哪个候选人"就是一条事实。事实表是**事件**，一直在增长。
- **集市表（mart_）**：把事实表按维度提前汇总好的结果表，**查询快**，但只是"缓存"，不是真相来源。

> 面试大白话："分析真相在事实表，集市表只是加速查询的汇总结果。"

## 二、维度表（4 张）

| 表 | 关键字段 | 作用 |
|---|---|---|
| `dim_candidate` | candidate_id、region、experience_years、education_level、current_title | 候选人画像 |
| `dim_job` | job_id、job_category（技术/销售/运营）、region、seniority_level（junior/mid/senior） | 岗位信息 |
| `dim_recruiter` | recruiter_id、region、team（如"华东招聘组"） | 顾问与团队 |
| `dim_model_version` | model_version（human_rule / ai_ranker_2026_q1 / ai_ranker_2026_q2）、deployed_at | 模型版本 |

## 三、事实表（2 张核心表）

### 1. `fact_recommendation`（一条推荐）

```text
recommendation_id    # 分析主键，一条推荐只计一次
candidate_id → dim_candidate
job_id       → dim_job
recruiter_id → dim_recruiter
model_version_id → dim_model_version
source       # ai / human  ← 本次分析的核心分组变量
recommendation_score  # AI 打分（0~1）
recommended_at        # 推荐时间（所有指标的归因时间）
```

### 2. `fact_funnel_event`（这条推荐后续的每个招聘阶段事件）

```text
recommendation_id → fact_recommendation
stage    # contacted / replied / interviewed / offered / hired
status   # completed / not_reached
event_at # 事件发生时间
```

**关键设计**：`recommendation_id + stage` 有**唯一约束**，防止同一阶段重复计数——比如一条推荐不会有两个"面试完成"事件。

## 四、为什么必须用事件级数据？（本项目最重要的设计决策）

早期版本只保留"按天汇总的看板指标"，后来发现三个致命问题：

1. **维度丢失**：日度汇总表没有模型版本、顾问团队，想按这些维度筛选就筛不了，或者口径不一致。
2. **滞后无法处理**：只有汇总数，不知道"1 月推荐的那批人，3 月才面试"——成熟队列根本算不出来。
3. **无法下钻**：效果异常想拆到"销售岗位 + 华东 + Q2 模型版本 + 华东招聘组"，没有事件级明细就做不到。

所以现在的原则（对应 ADR 0002）：

> **Dashboard 需要统一筛选时，一律从事件级事实层查询；`mart_*` 表只保留给可复用的日度、队列、漂移和告警汇总。**

## 五、集市表（5 张，由 `marts.py` 刷新）

| 表 | 内容 |
|---|---|
| `mart_daily_funnel` | 按日/来源/岗位/地区的漏斗计数与面试率 |
| `mart_cohort_conversion` | 按月队列的成熟转化率（30 天面试、90 天入职） |
| `mart_ai_effectiveness` | AI vs 人工的分子/分母/率/effect_size |
| `mart_feature_drift` | 特征漂移（PSI/JSD 的基线率 vs 当前率） |
| `mart_monitoring_alert` | 监控告警（严重程度、状态、证据） |

每条集市记录都带：**分子、分母、样本量、时间范围、metric_version（指标版本）**——这样：
- 可以校验指标口径；
- 可以幂等刷新（先删该版本再重算）；
- 为未来离线调度做准备。

## 六、合成数据怎么生成的（`seed.py`，面试必问"数据哪来的"）

- 固定随机种子 `20260722`，生成 8 万候选人、1500 岗位、10 万条推荐、约 60 万条事件。
- 数据范围 2026-01-01 至 2026-06-30，as-of 2026-07-15（模拟"现在"）。
- 刻意植入 **5 种可检测场景**（`detect_synthetic_scenarios()` 负责验证）：
  1. **选择偏差**：AI 推荐的候选人经验更高（`_pick_candidate` 里 AI 优先选经验≥5 年）。
  2. **模型退化**：2026 Q2 起，AI 推荐 + 销售岗位的面试概率下降 0.13。
  3. **联系延迟**：华东地区 2026 年 5 月的联系阶段延迟 3-6 天。
  4. **分数漂移**：2026 Q2 AI 推荐分数均值 +0.12。
  5. **未成熟队列**：as-of 日前 30 天内推荐的候选人还没到观察窗口。
- 对应测试 `tests/test_seed.py` 会验证这些场景能被稳定复现和发现。

> 面试金句："合成数据的价值不是模拟真实企业效果，而是**验证分析链路能不能发现问题**。"

## 七、外部真实数据（可讲可不讲）

项目还有一个 Kaggle "1.3M LinkedIn Jobs & Skills 2024" 导入模块（`linkedin_kaggle.py`），走 raw → staging → mart 分层，用于职位市场分析，**不**混入真实漏斗结果。公开仓库不含真实候选人身份。
