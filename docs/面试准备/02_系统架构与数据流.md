# 第 2 课：系统架构与数据流（面试必考）

## 一、整体架构图（先背这张图）

```
┌─────────────────────────────────────────────────────┐
│  前端：Streamlit 看板（8 个页面）                    │
│  首页 / 招聘漏斗 / 趋势分析 / 效果评估               │
│  模型监控 / 数据质量 / 机器学习洞察 / AI 分析助手     │
│  （app/ui.py 统一筛选：日期、来源、岗位、地区、      │
│    模型版本、顾问团队）                              │
└──────────────────────┬──────────────────────────────┘
                       │ HTTP JSON（app/api_client.py）
                       ▼
┌─────────────────────────────────────────────────────┐
│  后端：FastAPI 分析 API（src/aihr/api/main.py）      │
│  /api/v1/overview, funnel, effectiveness,            │
│  monitoring, data-quality, prediction-insights,      │
│  meta/filters, assistant/analyze ...                 │
│  Pydantic 响应模型 + 统一筛选参数                     │
└──────────────────────┬──────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────┐
│  服务层：src/aihr/services/analytics_core.py         │
│  漏斗 / 成熟队列 / IPTW / SMD / PSI / JSD /          │
│  数据质量规则 / 逻辑回归预测 / 孤立森林异常          │
└──────────────────────┬──────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────┐
│  数据库：PostgreSQL（本地可 SQLite）                  │
│  dim_* 维度表 → fact_recommendation →                │
│  fact_funnel_event → mart_* 集市表                   │
└─────────────────────────────────────────────────────┘
```

**一句话讲架构**："前端 Streamlit 负责展示和筛选，后端 FastAPI 负责统一接口，服务层负责所有指标和统计计算，数据库用维度表+事实表+集市表的分层设计。"

## 二、一次请求的完整旅程（以"招聘漏斗"页面为例）

1. 用户在 Streamlit 页面选择筛选条件（比如：2026 年 1-6 月、只选 AI 来源、销售岗位）。
2. `app/ui.py` 把筛选状态保存到 URL 参数 + 本地状态文件（`.aihr_filter_state.json`），保证**跨页面口径一致**。
3. `app/api_client.py` 向后端发 `GET /api/v1/funnel?start_date=...&end_date=...&source=ai&job_category=销售`。
4. FastAPI 入口（`api/main.py` 的 `funnel()` 函数）接收参数，调用服务层 `get_funnel(session, ...)`。
5. `analytics_core.py` 里 `get_funnel` 用 SQLAlchemy 查询 `fact_recommendation` 和 `fact_funnel_event`，按来源分组统计各阶段 completed 数量。
6. 结果以 Pydantic 模型校验后返回 JSON。
7. Streamlit 页面用 Plotly 画漏斗图，并展示 AI vs 人工的转化对比。

> 面试加分点：**"计算逻辑全部在后端服务层，前端只负责展示"** —— 这保证了同一指标在不同页面口径一致，也方便测试。

## 三、各层职责（面试问答素材）

| 层 | 文件 | 职责 | 面试怎么讲 |
|---|---|---|---|
| 前端看板 | `app/`（8 个页面 + ui.py + api_client.py） | 筛选、图表、结论展示 | "Streamlit 负责把结构化结论呈现给业务，不做指标计算" |
| API 层 | `src/aihr/api/main.py` | 应用生命周期、请求参数、响应模型、缓存、遥测 | "FastAPI 用 Pydantic 保证响应结构；统一 6 个筛选参数" |
| 服务层 | `services/analytics_core.py` 等 | 所有统计/ML 计算 | "核心分析方法都在这，前端/API 不掺和计算" |
| 数据访问 | `models.py` + SQLAlchemy | ORM 模型与查询 | "维度表 + 事实表 + 集市表的分层数仓设计" |
| 数据集市 | `services/marts.py` | 把事件级数据刷新成可复用汇总表 | "集市表带分子/分母/样本量/版本号，可幂等刷新" |
| 测试 | `tests/` | API、分析逻辑、种子数据验证 | "pytest 覆盖植入的 5 类异常场景都能被发现" |

## 四、统一筛选是怎么实现的（高频追问点）

6 个筛选维度：**开始日期、结束日期、推荐来源（ai/human）、岗位类别、地区、模型版本、顾问团队**。

- 前端：`app/ui.py` 用 `st.sidebar` 渲染筛选器，状态写入 URL 查询参数和本地 JSON 文件，切页面不丢。
- 后端：每个分析接口都接收同样的 6 个筛选参数，服务层用 `_recommendation_query(session, **filters)` 生成统一的条件查询。
- 效果：**任何一个页面、任何一个指标，筛选口径完全一致**。

> 面试常问："你们怎么保证不同页面指标口径一致？"
> 回答：筛选状态在 URL 参数 + 本地状态文件里共享；所有计算都走后端同一套 `_recommendation_query`，前端不做二次计算。

## 五、AI 分析助手（可选亮点，讲清楚边界）

- `app/analysis_assistant.py` 是**解释层，不是计算层**：先由页面加载结构化 API 数据，把当前筛选范围的指标上下文传给助手。
- 未配置外部 LLM 时，用**本地规则**生成"结论、事实、推断、建议"。
- 配置 DeepSeek（或任何 OpenAI 兼容服务）后，助手**只能引用传入的上下文**，被提示词约束为：不编造指标、不做因果声明、先提示数据限制。
- 服务端返回带**可信度信封**（样本量、时间范围、数据更新时间、质量状态），低置信度答案强制降级为"探索性判断"。

> 面试金句："LLM 不参与基础指标计算，只做解释；所有指标都来自结构化 API，LLM 无权编造数字。"

## 六、配置与运行环境（了解即可）

- 配置文件：`config/config.ini`（默认）、`config.local.ini`（本地 PostgreSQL）、`Test.ini`、`Online.ini`；环境变量 `AIHR_*` 可覆盖。
- 本地：`uvicorn aihr.api.main:app` + `streamlit run app/首页.py`；首次启动自动生成合成数据（`seed.py`）。
- Docker：`compose.yaml` 启动 PostgreSQL + API + Streamlit，含 health check。
- 生产化组件（本项目有，可作为加分项讲）：Redis 缓存 + RQ 预热、Prometheus 指标、Grafana 看板、OpenTelemetry、Alembic 迁移、操作端点 Bearer Token 鉴权。
