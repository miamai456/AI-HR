# AI 招聘推荐效果评估系统实施计划

## 1. 总体实施策略

项目按照“先数据、再指标、后页面，最后工程化”的顺序实施。每个阶段都必须产生一个可以运行和验证的结果，避免同时开发所有模块。

```text
需求与口径
  -> 项目骨架与开发环境
  -> 合成数据
  -> 数据库与 SQL 数据集市
  -> 基础 Dashboard
  -> 统计效果评估
  -> 漂移与异常诊断
  -> FastAPI 与 Docker
  -> 测试、文档和作品集包装
```

建议投入 5 至 6 周，每周 15 至 20 小时。若时间有限，应优先完成阶段 0 至阶段 5。

## 2. 阶段 0：冻结 MVP 范围

### 目标

确保项目只围绕 AI 推荐效果评估展开。

### 任务

- 阅读并确认 `需求.md` 中的指标口径。
- 确定主指标为“推荐后 30 天合格面试率”。
- 确定默认成熟窗口：面试 30 天，入职 90 天。
- 确定首版分析维度：岗位类别、地区、候选人经验、顾问团队、模型版本。
- 建立 `docs/metric_dictionary.md`，详细记录分子、分母、时间字段和过滤规则。

### 验收

- 每个 Dashboard 指标都能在指标字典中找到唯一口径。
- 不存在“后续再决定分母”的指标。

## 4. 阶段 2：实现合成数据生成器

### 目标

产生结构合理、可重复并包含已知业务问题的数据。

### 实施顺序

1. 生成岗位、候选人、顾问和模型版本维度。
2. 根据岗位难度和候选人特征生成推荐关系。
3. 模拟 AI 与人工推荐分配机制，制造可观测选择偏差。
4. 依次生成联系、回复、面试、Offer 和入职事件。
5. 为每个阶段生成合理的时间间隔和失败原因。
6. 植入需求书中定义的版本、地区、顾问和成熟度异常。
7. 输出 Parquet 样本，并支持写入 MySQL。

### 推荐配置方式

```yaml
seed: 20260722
n_candidates: 80000
n_jobs: 1500
n_recommendations: 150000
start_date: 2025-07-01
end_date: 2026-06-30
scenarios:
  ai_selection_bias: true
  sales_v2_degradation: true
  east_china_contact_delay: true
  v3_feature_drift: true
```

### 需要编写的测试

- 相同随机种子产生相同记录。
- 主键唯一且外键有效。
- 事件顺序符合招聘流程。
- 所有概率字段位于 0 至 1。
- 植入场景在总体方向上符合配置。

### 验收

- 一条命令生成完整数据。
- 生成过程输出记录数、日期范围和场景摘要。
- 150,000 条推荐数据在普通电脑上可接受时间内生成。

## 5. 阶段 3：搭建 MySQL 与 SQL 数据集市

### 目标

将原始事件转换为稳定、可复用的分析表。

### 实施顺序

1. 编写维度表和事实表 DDL。
2. 为日期、推荐来源、岗位、地区和模型版本建立必要索引。
3. 编写原始数据导入脚本。
4. 创建推荐粒度的漏斗宽表，每条推荐一行。
5. 创建日度漏斗、月度队列、效果评估、漂移和告警数据集市。
6. 编写数据质量 SQL。

### 推荐粒度宽表字段

```text
recommendation_id
recommended_at
source
job_category
region
model_version
contacted_flag
replied_flag
interviewed_flag
offered_flag
hired_flag
days_to_contact
days_to_interview
is_30d_mature
is_90d_mature
```

### 验收

- 任意 Dashboard 指标能够从 `mart_*` 表直接查询。
- 同一指标在 SQL 和 Python 中计算结果一致。
- 漏斗分子不大于分母。
- 未成熟数据具有明确标识。

## 6. 阶段 4：完成基础 Streamlit Dashboard

### 目标

先让系统能够被浏览和演示，再增加高级统计方法。

### 页面开发顺序

1. 总览页：KPI、趋势、来源对比、告警列表。
2. 漏斗与队列页：漏斗图、队列热力图、各环节耗时。
3. 效果评估页：分群转化率和置信区间。
4. 模型监控页：模型版本趋势和分布对比。
5. 数据质量页：缺失、重复、非法顺序和延迟。

### 开发约束

- 页面只负责交互和渲染，不直接编写复杂 SQL。
- 数据读取统一放入 `repositories/`。
- 指标计算统一放入 `metrics/`。
- Plotly 图表封装为可复用组件。
- 所有页面共享同一套筛选条件和颜色规则。
- 使用 Streamlit 缓存降低重复查询。

### 验收

- 修改岗位、地区或日期后，所有图表同步更新。
- 所有比率能查看分子和分母。
- 未成熟队列在页面上有明确提示。
- 页面在 1366x768 和移动端宽度下无内容重叠。

## 7. 阶段 5：实现统计效果评估

### 目标

从简单转化率对比升级为具有统计可信度的效果评估。

### 实施顺序

1. 计算 AI 与人工推荐的原始比例差和 95% 置信区间。
2. 使用 statsmodels 建立面试结果 Logistic 回归。
3. 使用推荐发生前特征估计倾向得分。
4. 检查 AI 与人工组的倾向得分重叠区域。
5. 使用加权或匹配构建更可比的样本。
6. 计算调整前后的 SMD。
7. 估计调整后的 30 天合格面试率差异和置信区间。
8. 对岗位、地区等分群设置最小样本量要求。

### 页面应展示

- 原始效果差异。
- 调整后效果差异。
- 置信区间和样本量。
- SMD 调整前后对比图。
- 倾向得分分布图。
- 方法假设和限制说明。

### 验收

- 能发现 AI 组和人工组在生成数据中的初始不平衡。
- 调整后的大多数特征达到预设平衡标准。
- 原始效果与调整后效果存在合理差异。
- 测试确认没有使用处理后变量。

## 8. 阶段 6：实现漂移监控和异常诊断

### 目标

发现模型输入、人群结构和转化效果变化，并给出可验证的原因线索。

### 实施顺序

1. 确定每个模型版本的基准期。
2. 对工作年限、推荐分数等数值特征计算 PSI。
3. 对岗位类型、地区等类别特征计算 JSD。
4. 对核心转化率建立滚动基准和告警规则。
5. 将总体变化拆解为分群占比变化和分群内效果变化。
6. 建立告警严重程度、状态和证据字段。
7. 将已植入异常与检测结果逐项对照。

### 验收

- 能识别 V3 特征漂移。
- 能识别 V2 销售岗位效果下降。
- 能识别华东顾问联系延迟。
- 告警包含基准期、当前期、样本量、阈值和贡献维度。

## 9. 阶段 7：增加 FastAPI 和 Docker Compose

### 目标

展示系统分层和可复现部署能力。

### 实施顺序

1. 将 Dashboard 使用的查询封装为服务函数。
2. 增加 FastAPI 健康检查和只读查询接口。
3. 使用 Pydantic 定义筛选参数和响应结构。
4. 使用 Alembic 管理数据库结构变更。
5. 为 Streamlit、FastAPI 分别编写 Dockerfile。
6. 使用 Compose 管理 MySQL、API 和 Dashboard。
7. 增加服务健康检查和启动依赖。

### 验收

- `docker compose up --build` 能启动全部服务。
- `/api/v1/health` 返回服务和数据库状态。
- `/docs` 可以查看和调用 API。
- Dashboard 通过 API 获取核心指标。
- 容器重启后 MySQL 数据仍然保留。

## 13. 立即开始的第一批任务

按以下顺序开始编码：

1. 创建项目目录、`pyproject.toml` 和 `config/*.ini`。
2. 创建 `docs/metric_dictionary.md`。
3. 定义 5 张核心业务表的 DDL。
4. 编写候选人和岗位维度生成器。
5. 编写推荐及漏斗事件生成器。
6. 为固定种子、主键、外键和事件顺序编写测试。
7. 生成第一批 10,000 条小样本并人工检查。
8. 小样本通过后再扩展到 150,000 条。

第一批任务完成后，再开始 Dashboard。这样页面使用的是经过校验的数据和指标，而不是边画图边修改数据结构。
## 14. 本地数据库配置

本地开发默认使用 `config/config.ini` 中的 SQLite。需要连接 PostgreSQL、MySQL 或其他数据库时，
请通过 `AIHR_DATABASE_URL` 环境变量或本地私有配置文件提供连接串；不要把真实账号、密码或连接信息提交到仓库。

完整启动、Docker 配置和验证流程见 [运行与验证](运行与验证.md)。
